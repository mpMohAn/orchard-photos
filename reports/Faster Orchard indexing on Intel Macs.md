# Faster Orchard indexing on Intel Macs

Orchard has several credible indexing improvements to test, with the strongest immediate opportunities in **scheduling and repeated work**. The current implementation already caches thumbnails, skips unchanged files, batches visual inference and uses a turbo-backed JPEG decoder. Source inspection identified a whole-job lock that delays People, a pause path that retains that lock, repeated same-batch duplicate decoding and repeated face-prototype database reads. The vision model remains full precision, which gives quantization a meaningful experimental target. Your Mac also has a Radeon Pro 560X and an available Core ML execution provider, although efficient execution of this graph on that GPU remains unverified. **The recommended sequence is to establish stage timings, fix resource ownership, reduce repeated work, tune the existing runtime, then compare precision and GPU alternatives.** Research supports those experiments, while a representative Intel benchmark is still needed to establish their speed gains. [Current visual pipeline](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/semantic.py), [current People pipeline](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/faces.py)

Research completed on 12 November 2026, Asia/Kolkata. Application findings refer to source commit `3d21c0a330838327e949b1d7bb433563fff88fb8`. Evidence comprises primary documentation, research papers, source inspection, existing benchmark reports and read-only runtime/hardware metadata. The performance experiments described below are proposed work.

## Existing optimizations narrow the useful changes

Read-only system metadata identified an **Intel Core i7-8850H at 2.60 GHz, six physical cores, twelve logical processors and 16 GiB RAM**, running macOS 14.4.1. Graphics metadata identified Intel UHD Graphics 630 with 1,536 MB shared memory and a **Radeon Pro 560X with 4 GB VRAM**. Those observations establish available hardware. They leave model compatibility, sustained throughput, thermal behavior and GPU utilization to measurement. The metadata query did not establish a Metal capability/version.

The scanner already compares file size and modification time against the catalog, hashes changed content with SHA-256, uses up to eight scanner workers and commits in 48-file batches. Its decoded-image budget is 1 GiB. It applies JPEG scaled decoding and EXIF orientation, then creates 720-pixel WebP thumbnails. Read-only introspection found Pillow 12.3.0 already using libjpeg-turbo in both the development environment and the workspace-built app. A separate TurboJPEG wrapper therefore needs an advantage over this existing implementation. [Scanner](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/scanner.py#L35), [scaled decoding](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/scanner.py#L223), [Pillow feature introspection](https://pillow.readthedocs.io/en/stable/reference/features.html)

Visual search reads those cached thumbnails and prepares 256×256 model inputs. It already executes batches of up to sixteen images and saves vectors in batches. Inspection of the existing CPU graph's protobuf metadata found a symbolic batch dimension, so the current CPU path can pass the prepared batch in one model call. The image encoder uses the approximately 372 MB **FP32 vision graph**, while the text encoder is already INT8. The code's model-run helper also supports fixed-batch exports, making graph shape an important detail for every future candidate. [Semantic indexing and preprocessing](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/semantic.py#L424), [model execution](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/semantic.py#L290), [ONNX model schema](https://github.com/onnx/onnx/blob/main/onnx/onnx.proto)

The relevant work has several distinct completion points. Gallery thumbnails become available before all images are searchable, and People has its own detector, alignment, recognition and matching work. Exact-copy files share an image identity and visual embedding. Consequently, a benchmark should record both file paths and unique content IDs. A duplicate-heavy import can have considerable scanning work and relatively little new model work. [Scanner schema](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/scanner.py#L256), [pending embeddings](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/semantic.py#L404)

```text
Directory discovery and change detection
              ↓
SHA-256 identity, metadata and cached thumbnail generation
              ↓
Cached thumbnail → tensor preparation → visual inference → vector commit
              ↓
Near-duplicate regrouping

People currently waits for shared resource ownership
              ↓
Original verification → decode → face detection → alignment
              ↓
Face recognition → person matching → per-image checkpoint
```

Earlier measurements provide a useful warning about thread limits. Three twelve-PNG runs with automatic threads had a median visual-ready time of **7.435 seconds**, compared with **9.119 seconds** for two threads. Median sampled CPU time, including the sampler, was 24.805 seconds with automatic threads and 15.964 seconds with two. These startup-including, synthetic runs show a wall-time/CPU-cost trade-off. They provide insufficient evidence for selecting the fastest sustained setting for a mixed 2,000-photo library. Likewise, the fifty-image People report uses brightness variants of one public face sample, and the 10,000-image gallery test excludes inference. [Existing thread reports](https://github.com/mpMohAn/orchard-photos/tree/3d21c0a330838327e949b1d7bb433563fff88fb8/docs/benchmarks/2026-11-05), [People workload](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/docs/benchmarks/2026-11-11/people-performance.json), [gallery workload](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/docs/benchmarks/2026-11-06/workspace-ui-10000.json)

## Short resource leases address verified People starvation

`Library.index()` holds `semantic_lock` across the entire visual backlog and subsequent near-duplicate regrouping. People waits while that lock is held. The visual worker reaches its pause checkpoint after acquiring the outer lock, so pausing visual indexing can leave People waiting until visual indexing resumes. This is a **verified progress and ownership problem**, with a direct source-level fix to design. Faster overall completion is a separate outcome to evaluate. [Library ownership](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/library.py#L120), [visual pause checkpoint](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/semantic.py#L430), [pause implementation](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/indexing.py)

A suitable first design gives one bounded inference unit a resource lease, then chooses the next eligible task. A unit could be one visual batch or a bounded amount of face work. The worker releases ownership before waiting for pause, input preparation, an empty queue or another turn. Foreground text/image queries need a scheduling opportunity because `Encoder.features()` currently shares one lock across text and image inference. Preserve atomic vector batches, per-image face checkpoints, cancellation generations and one active worker per logical task. [Shared inference lock](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/semantic.py#L223), [People checkpointing](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/faces.py#L169)

Fair turns should make the first People result arrive earlier and prevent indefinite waiting. Their effect on total completion depends on cache behavior, batch efficiency, thermal pressure and scheduling overhead. A six-core CPU can already be heavily occupied by one well-parallelized model. Starting both inference engines together introduces additional thread pools and working sets, so bounded concurrency belongs in a later comparison against a measured exclusive-owner baseline. [ORT thread management](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)

People also sleeps **50 ms after every image**. For 2,296 images, that contributes **114.8 seconds of deliberate delay**, calculated directly from the code. It is an arithmetic contribution, with overlap and other work determining the total elapsed time. Replacing this fixed charge with a measured work/rest budget is a concrete experiment. The controller should respond to recent processing cost and foreground latency, including cheap no-face images and crowded group photos. Higher sustained CPU use and heat are possible costs. [People worker](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/faces.py#L169)

The face worker currently loads its model sessions before entering the wait loop. Deferring session creation until its first lease can reduce RAM retained during a long visual-only phase. A bounded warm-retention period could subsequently help sporadic arrivals. Measure setup time, first-result latency, waiting RSS and combined peak memory for both policies. Existing face-only memory numbers cannot describe simultaneous search, People and browser memory use. [Face loading and waiting](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/faces.py#L169)

Newly downloaded images also need queue attention. Visual indexing already sorts pending work by displayed photo date, but drains a snapshot before querying arrivals again. An old photograph downloaded today can have an old capture date. A bounded recent-arrival share, combined with increasing priority for older queued work, can reduce arrival-to-searchable delay while allowing the initial backlog to complete. [Pending ordering](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/semantic.py#L403)

## Pipeline overlap and exact caches target repeated work

The current visual loop prepares a batch, executes inference, commits it, then starts preparing the next batch. A bounded producer can prepare the next batch during inference. Start with one preparation worker and queue depth one. Compare depth two only if preparation leaves measured gaps. A sixteen-image float32 tensor at 3×256×256 is **12 MiB**, before decoded thumbnails and temporary arrays. Queue limits therefore need byte accounting as well as an item count. [Current loop](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/semantic.py#L430), [Python bounded queues](https://docs.python.org/3.13/library/queue.html)

The preparation boundary matters. Calling today's `Encoder.features()` from a prefetch thread would still perform tensor preparation inside its lock. Separate deterministic pixel preparation from session execution while retaining the current RGB conversion, interpolation, normalization and channel ordering. Verify image/vector ID alignment, cancellation cleanup and exception propagation. Overlap saves time only when preparation can use resources that inference leaves available. [Current preparation boundary](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/semantic.py#L223)

A smaller repeated-work fix concerns exact copies. Scanner workers consult `_seen`, but the set updates after the full 48-file batch returns. Multiple identical new files in one batch can therefore decode and encode the same thumbnail independently. A hash-keyed in-flight result, or a staged hash/decode design, could let those paths share the first successful result. Recovery must handle producer failure and preserve per-path errors. **SHA-256 identity and native Trash revalidation remain part of the correctness contract.** Faster non-cryptographic or perceptual hashes can serve candidate roles only with appropriate final verification. [Same-batch scanner behavior](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/scanner.py#L281), [content and file validation](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/duplicates.py#L95)

Face matching has another scalable target. For every detected face, `_store()` queries existing non-ignored faces grouped by person, obtains a representative vector, performs Python-level candidate dot products and sorts the results. An exact cached prototype matrix can reduce repeated SQL and Python work. It needs invalidation for additions, removals, naming-related state where relevant, merge, assignment, separation, ignore and clear actions. It must preserve the exclusion of a person already represented by another face in the same image. Changing representatives to centroids introduces a further matching-quality experiment. [Current matching and corrections](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/faces.py#L229)

SQLite already uses WAL and batch writes. Profile connection creation, writer waits, commits, checkpoints and People status queries before adding indexes or changing transaction policy. `People.status()` currently combines cleanup writes with group aggregation, which creates an opportunity for cached read-only status and cleanup at controlled points. Worker-owned connections and bounded commit grouping merit testing only when those costs matter, while per-image face/result atomicity and crash recovery remain necessary. [Cache helper](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/cache.py#L15), [People status](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/faces.py#L155), [SQLite WAL](https://www.sqlite.org/wal.html), [query-plan diagnostics](https://www.sqlite.org/eqp.html)

Near-duplicate grouping still performs chunked all-pairs vector comparisons and rewrites group membership after updates. Chunking bounds temporary memory, while arithmetic remains quadratic. For scale, a 2,048×100,000 float32 similarity block alone occupies about 781 MiB. Incremental comparisons between new and existing images could help frequent small imports. Removals and transitive grouping links need explicit handling. Faiss or HNSW can later generate approximate candidates, followed by exact checks, with threshold-neighbor recall measured against the exact baseline. Their construction, deletion and maintenance costs determine the useful crossover. [Near-duplicate grouping](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/groups.py#L52), [Faiss index guidance](https://github.com/facebookresearch/faiss/wiki/Guidelines-to-choose-an-index), [hnswlib maintenance constraints](https://github.com/nmslib/hnswlib)

Decoder and file-event replacements have narrower roles. Pillow already applies JPEG draft decoding and an optimized thumbnail resize. ImageIO offers native bounded, orientation-aware thumbnails, and libvips offers codec-dependent shrink-on-load with its own threading. Compare them on actual JPEG, HEIC, PNG and TIFF costs before accepting codec, color, alpha and packaging changes. Sharing today's lossy WebP with face detection requires small-face, landmark and recognition tests because People currently derives its 640-pixel input from the original. Native FSEvents can reduce idle directory-probe work on large trees, with reconciliation retained for coalesced or dropped events. [Pillow thumbnail behavior](https://pillow.readthedocs.io/en/stable/reference/Image.html#PIL.Image.Image.thumbnail), [Apple ImageIO](https://developer.apple.com/documentation/imageio/cgimagesourcecreatethumbnailatindex(_:_:_:)), [libvips shrinking](https://github.com/libvips/libvips/wiki/HOWTO----Image-shrinking), [libvips threading](https://www.libvips.org/API/current/using-threads.html), [Apple FSEvents](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html)

## Precision and GPU routes need separate compatibility checks

For this six-physical-core Mac, screen CPU thread counts **1, 2, 4, 6 and automatic**, then test promising batch/thread combinations. The twelve logical processors share physical execution resources. Compare supported spinning controls because active waiting trades energy for latency. The pinned ORT 1.23.2 source contains on/off spinning keys, while newer rolling documentation describes additional duration/backoff options. Every selected option needs verification against the shipped runtime. Native global pools require additional Python/native integration investigation. [ORT threading guidance](https://onnxruntime.ai/docs/performance/tune-performance/threading.html), [version-pinned configuration keys](https://raw.githubusercontent.com/microsoft/onnxruntime/v1.23.2/include/onnxruntime/core/session/onnxruntime_session_options_config_keys.h)

**INT8 vision is a credible precision experiment because the current vision graph is FP32.** Quantization format, supported operators and calibration affect both accuracy and speed. ONNX Runtime documents x86-specific signedness/saturation considerations and cases where quantization overhead worsens performance. Compare actual end-to-end results with the existing graph. Measure embedding drift, text-to-image retrieval, image-to-image ranking and duplicate-group stability. The already-INT8 text model should remain a compatible paired baseline during that experiment. [ORT quantization guidance](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)

**Core ML deserves a controlled Intel GPU experiment.** Read-only introspection found `CoreMLExecutionProvider` in the existing Intel ORT 1.23.2 provider list, alongside CPU and Azure providers. Orchard's gate currently restricts Core ML to arm64. Official provider documentation describes CPU/GPU execution and shape-related performance considerations. Test whether this graph receives substantial GPU execution, how unsupported nodes fall back, and whether compilation/transfer costs erase useful savings. Record cold compilation separately from warm throughput, and check foreground WebKit responsiveness while GPU work runs. Provider presence and Radeon VRAM establish feasibility questions, with performance still unresolved. [Current provider gate](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/semantic.py#L268), [ORT Core ML provider](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html), [Apple CPU/GPU compute units](https://developer.apple.com/documentation/coreml/mlcomputeunits/cpuandgpu)

OpenVINO is a lower-priority route for this deployment. Its 2025 release notes discontinued macOS x86 validation and announced later support removal. The 2026 general CPU support matrix lists macOS ARM64. The same requirements page retains a distribution-specific npm paragraph describing macOS x86_64 CPU inference, so support must be verified for the exact binding and release. That evidence does not establish a supported replacement for Orchard's Python 3.13 Intel package. Older working releases add maintenance and packaging questions. [OpenVINO 2025 deprecation](https://docs.openvino.ai/2025/about-openvino/release-notes-openvino.html), [OpenVINO 2026 requirements](https://docs.openvino.ai/2026/about-openvino/release-notes-openvino/system-requirements.html)

Apple's MobileCLIP and MobileCLIP2 offer smaller-model candidates worth comparing after the existing pipeline is characterized. Published mobile latency and zero-shot results apply to their reported devices and tasks. An Intel experiment needs a verified export, tokenizer, preprocessing and paired image/text encoders, followed by representative retrieval evaluation. A new search model needs a separately versioned search index and a reindexing plan. People uses separate YuNet/SFace models and versioning, so a search-model change alone does not establish a need to rebuild People. Shared image preprocessing or a face-model change introduces its own quality checks. [Official MobileCLIP repository](https://github.com/apple-aiml-research/ml-mobileclip), [MobileCLIP paper](https://arxiv.org/abs/2311.17049), [MobileCLIP2 paper](https://arxiv.org/abs/2508.20691), [Orchard search identity](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/semantic.py), [separate People identity](https://github.com/mpMohAn/orchard-photos/blob/3d21c0a330838327e949b1d7bb433563fff88fb8/server/faces.py)

## Bounded experiments can choose a release configuration

The practical comparison is staged. Start with stage traces and a small representative slice, screen a few settings, then take two or three finalists to larger mixed libraries. A full Cartesian sweep of every setting, corpus and cache state would consume substantial time before producing a useful decision.

| Approach | Main outcome to test | Principal trade-off | Proposed priority |
| --- | --- | --- | --- |
| Release ownership before pause/wait | People progress and bounded waiting | Scheduling and recovery correctness | Immediate verified fix |
| Short fair inference leases | Earlier People and foreground results | Batch efficiency and switching overhead | First scheduler comparison |
| Time-budgeted People yielding | Reduce fixed-delay overhead | Sustained CPU, heat and interaction latency | Early throughput experiment |
| Bounded next-batch preparation | Hide preparation gaps | Extra CPU/bandwidth and queued RAM | Early pipeline experiment |
| Same-batch SHA result reuse | Avoid repeated duplicate decoding | In-flight failure/cancellation handling | Early, duplicate-heavy imports |
| CPU thread/batch tuning | Better throughput/resource balance | Text-query latency, RAM and thermal load | Early coarse screen |
| Exact People prototype cache | Reduce repeated SQL/Python matching | Comprehensive invalidation | After matching-stage profiling |
| Incremental duplicate grouping | Reduce small-import regrouping | Removal and graph-link correctness | When grouping cost grows |
| INT8 vision | Reduce model compute/memory demand | Retrieval drift and hardware dependence | Precision experiment |
| Intel Core ML GPU | Offload supported model work | Compatibility, compilation and fallback | Separate hardware experiment |
| Smaller paired search model | Lower ongoing inference cost | Relevance, export and reindexing cost | Later model comparison |
| ImageIO/libvips | Reduce measured decode/resize costs | Codec parity and native packaging | Format-specific experiment |
| ANN/FSEvents/database policy | Scale relevant maintenance costs | Recall, reconciliation or durability | Profile-dependent later work |

Instrumentation should separate listing, hashing, original decode, thumbnail encoding, cached-thumbnail reading, tensor preparation, session setup, inference, face alignment, matching, commits and regrouping. Queue and lock waits need their own spans. ORT's profiler can expose operator/thread timings, while Instruments helps distinguish busy execution from blocked threads. Use low-instrumentation timing runs separately from traces. [ORT profiling](https://onnxruntime.ai/docs/performance/tune-performance/profiling-tools.html), [Apple Instruments](https://help.apple.com/xcode/mac/current/en.lproj/devcc15e6912.html), [Apple hang analysis](https://developer.apple.com/tutorials/instruments/getting-started-with-hang-analysis)

A bounded first screen can use approximately 100 varied, authorized/public images with models already cached. Start by varying threads at the existing batch size, then compare batches **1, 2, 4, 8 and 16** for the most promising thread settings. Keep queue depth zero as the baseline and compare one prepared batch before considering two. Record the exact graph shape, runtime/provider, model hashes, preprocessing, power source and storage. Compare configurations in alternating order under matched background activity and repeat finalists enough to distinguish gains from variation. Use a separate realistic-interaction stress run to evaluate contention. Existing methodology supports warmups, repeated processes and recording system effects. [pyperf run methodology](https://pyperf.readthedocs.io/en/stable/run_benchmark.html), [system effects](https://pyperf.readthedocs.io/en/stable/system.html)

Take the best two or three candidates to a roughly 2,500-image mixed library, then a 10,000-image scaling case where justified. Cover large JPEGs, HEIC, PNG, tiny assets, EXIF rotation, alpha, exact copies, near-duplicates, no-face photos and crowded scenes. Include arrivals of 1, 20 and 100 files, incomplete downloads, pause/resume, restart and library switches. Use public or specifically authorized material. Separate model downloading, cold process startup, cold sessions and warm operation, and label filesystem-cache conditions explicitly.

Report first gallery tile, first searchable image, first People group and full completion of each service. Pair images/second with CPU-seconds/image, peak and steady RSS, memory pressure, swap, disk traffic and foreground gallery/preview/query p50, p95 and p99 latency. Measure visible input-to-result behavior as well as HTTP latency. Include a sustained run after thermal settling. Apple's QoS and thermal APIs offer policy inputs, with actual propagation to Python and native inference workers requiring measurement. [Apple task prioritization](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/PrioritizeWorkAtTheTaskLevel.html), [thermal state](https://developer.apple.com/documentation/foundation/processinfo/thermalstate-swift.enum.md)

Acceptance budgets should follow the baseline and the user's responsiveness preference. A throughput candidate should show repeatable improvement larger than observed variation, bounded memory and acceptable foreground latency. Scheduling/cache changes should preserve functional results and durable recovery. Precision/model changes need paired retrieval judgments, top-k ranking comparisons and duplicate-group checks. Changes to face inputs or matching need false-merge, false-split, missed-face and manual-correction tests. The representative corpus, combined model-memory peak and useful absolute latency budgets remain open decisions.

## Conclusion

The next implementation decision can preserve the current search model while addressing verified ownership problems and testing exact work reuse. That provides a stable reference for evaluating precision and GPU changes. A migration to a different model earns its cost only after future processing savings exceed conversion, validation and reindexing time, making library growth and incremental import patterns important to the choice. The resulting benchmark should identify both the best sustained completion setting and a browsing-safe operating point, so the release default reflects an explicit performance trade-off.
